# commit: 변경사항 분석 후 한국어 커밋

변경사항을 스스로 판단해 의미 있는 한 개의 커밋으로 정리하는 것이 목표다. 여러 성격의 변경이 섞여 있어도 커밋은 분리하지 않고, 대신 커밋 메시지 본문에서 각 단위를 명확히 설명해 히스토리를 읽는 사람이 무엇이 왜 바뀌었는지 알 수 있게 한다.

## Step 1: 변경사항 파악

`git status`, `git diff`, `git diff --cached`로 스테이징 여부와 무관하게 전체 변경사항을 확인한다. untracked 파일도 새로 추가된 코드일 수 있으므로 함께 검토한다.

- 현재 디렉토리가 git 저장소가 아니면 그 사실을 안내하고 종료한다.
- 커밋할 변경사항이 전혀 없으면 그 사실을 안내하고 종료한다.

## Step 2: 논리적 단위로 분류

변경사항을 성격별로 나눠본다 (예: 새 기능, 버그 수정, 구조 개선, 설정/빌드 변경 등). 이 분류는 커밋을 쪼개기 위한 것이 아니라, 다음 단계에서 메시지를 정확히 쓰기 위한 것이다 — 하나의 커밋에 여러 단위가 섞여 있다면 본문에 bullet로 각각 설명한다.

## Step 3: 대표 타입 선택과 메시지 작성

가장 비중이 크거나 영향이 큰 변경을 기준으로 타입을 하나 고른다. 지원하는 타입은 다음 네 가지로 한정한다:

- `feat`: 새로운 기능/동작 추가
- `fix`: 버그 수정
- `refactor`: 동작 변경 없는 구조 개선
- `chore`: 그 외 (설정, 의존성, 빌드 스크립트 등)

**형식**

```
type: 한 줄 요약 (한국어, 무엇이 바뀌었는지 명확하게)

- 세부 단위 1 설명 (여러 논리적 단위가 섞였을 때만)
- 세부 단위 2 설명
```

단일 논리 단위만 있다면 본문 없이 제목 한 줄로 충분하다. 요약은 "~함", "~추가" 처럼 개조식으로 간결하게 쓰고, "무엇을"보다 "왜"가 드러나면 더 좋다.

## Step 4: 안전 점검

`.env`, 자격증명, 키 파일 등 민감한 파일이 변경 목록에 있으면 커밋 대상에서 제외하고 사용자에게 알린다. `git add -A`처럼 전체를 뭉뚱그려 스테이징하지 말고, 커밋에 포함할 파일을 하나씩 명시해서 스테이징한다 — 의도치 않은 파일이 섞여 들어가는 것을 막기 위함이다.

## Step 5: 사용자 승인

커밋을 실행하기 전에 반드시 다음을 함께 보여주고 승인을 받는다:

- 작성한 커밋 메시지 전문
- 이 커밋에 포함될 파일 목록

사용자가 수정을 요청하면 메시지나 파일 목록을 반영해 다시 보여준다. 승인 전에는 어떤 경우에도 `git commit`을 실행하지 않는다.

## Step 6: 커밋 실행

승인을 받으면 승인된 파일만 `git add`로 스테이징한 뒤 `git commit -m`으로 커밋한다. 커밋 후 `git status`로 결과를 확인하고 사용자에게 짧게 보고한다.

- `--no-verify`, `--amend`, `push --force` 등은 사용자가 명시적으로 요청하지 않는 한 사용하지 않는다.
- 사용자가 명시적으로 push까지 요청한 게 아니라면 커밋만 하고 원격에 push하지 않는다.
