# TDD Rule

> ⚠️ **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** "이번만 예외로", "일단 먼저 짜고 나중에 테스트" 같은 해석은 허용되지 않는다.

## 0. 우선순위: 프로젝트별 규칙이 항상 우선한다

- 현재 작업 중인 프로젝트의 **`CLAUDE.md` / `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 그 규칙을 우선 적용**한다.
- 이 파일(`.claude/rules/tdd.md`)은 프로젝트별 규칙이 없을 때 적용되는 **기본값(fallback)**이다.
- 충돌 시: 프로젝트 규칙 > 이 파일.

## 1. 적용 기준

### TDD를 반드시 적용해야 하는 대상

- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이 등)
- **API** (요청/응답 처리, 라우팅, 유효성 검증 로직)
- **유틸리티 함수** (순수 함수, 데이터 변환, 파서 등)
- **버그 수정** (재현 테스트가 곧 RED)

### TDD가 불필요한 대상

- **타입 정의** (interface, type alias 등 — 실행되지 않는 선언)
- **설정 파일** (config, env, build 설정 등)
- **순수 UI (마크업/스타일)** — 로직이 없는 렌더링 전용 컴포넌트
- **SQL** (스키마/마이그레이션 자체. 단, SQL을 호출하는 비즈니스 로직은 대상에 포함)

## 2. RED-GREEN-REFACTOR 사이클

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 마라.
- 테스트 작성 후 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않은 테스트는 존재하지 않는 테스트다.
- 실패 이유는 **오직 "기능 미구현"**이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED가 아니라 그냥 버그다 — 고치고 나서 다시 실패를 확인하라.

### GREEN

- **테스트를 통과시키는 데 필요한 최소한의 코드만 작성**한다.
- **YAGNI 원칙** — 지금 테스트가 요구하지 않는 기능, 파라미터, 분기를 미리 만들지 마라.
- 통과 확인은 **신규 테스트 + 기존 테스트 전체**로 한다. 일부만 돌리고 넘어가지 마라.

### REFACTOR

- 이 단계에서 하는 일: **중복 제거, 이름 개선, 헬퍼 추출**뿐이다.
- **새로운 동작을 추가하지 마라.** 새 동작이 필요하면 다음 RED로 넘어가야 한다.
- 리팩터링 중에도, 끝난 후에도 **테스트는 계속 green이어야 한다.**

### 반복

- REFACTOR가 끝나면 **다음 동작의 RED로 돌아간다.** 사이클은 대상 기능이 끝날 때까지 반복.

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작**한다.
- "일단 남겨두고 나중에 테스트만 추가하면 되지 않나"는 허용되지 않는다.
- **"참고용으로 남긴다"는 것도 금지.** 주석 처리든 별도 파일이든, 테스트 없이 작성된 프로덕션 코드는 존재해서는 안 된다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용도 낮다. 단순함은 테스트를 생략할 이유가 아니라 테스트가 쉬운 이유다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. 테스트 없는 코드는 이미 "완료되지 않은 것"이다 — 지금 하지 않으면 영원히 안 한다. |
| "시간이 없다" | 테스트 없이 짠 코드의 디버깅 시간이 테스트 작성 시간보다 항상 더 든다. TDD는 시간을 아끼는 방법이지 쓰는 방법이 아니다. |
| "삭제하면 낭비" | 테스트 없이 작성된 코드는 검증되지 않은 코드다. 검증되지 않은 코드를 남기는 것이야말로 낭비다. |
| "프로토타입이다" | 프로토타입은 살아남아 프로덕션이 된다. "임시"라는 이름표는 사라지고 코드만 남는다. |
